# 사용자 ID 기준 DB 전환

## 적용한 이관 방식

2026-09-21 사용자가 선택한 정책: **기존 기록은 보관하고 ID 기준으로 새로 시작한다.**

- 기존 스프레드시트의 `DB` 탭은 그대로 보관한다.
- 같은 문서에 새 `DB_UserId` 탭을 만들었다. 계정 정보는 이 탭에 저장하며, 방 상태·입퇴장·닉네임 이력은 별도 활동 탭에 저장한다.
- 기존 닉네임과 일치하더라도 포인트·인기도·기여도·암호를 가져오지 않는다.
- 수신을 시작한 뒤 확인되는 작성자 ID와 조회·인기도 명령의 멘션 대상 ID마다 새 계정을 등록한다. 포인트·인기도·기여도는 0부터 시작한다.
- 같은 ID가 새 닉네임으로 메시지를 보내면 표시 이름을 갱신하고 기존 자산을 유지한다. 같은 닉네임의 다른 ID는 별도 계정이다.

## 시트 구조

1행은 아래 헤더이고, 2행부터 사용자 데이터다. 헤더 이름과 순서는 코드에서 검사한다.

| 열 | 헤더 | 내용 |
| --- | --- | --- |
| A | nickname | 최근 확인한 표시 이름 |
| B | take_attendance | 출석 표시 |
| C | attendance_at | 마지막 출석 시각, ISO 8601 문자열 |
| D | point | 포인트 |
| E | popularity | 인기도 |
| F | password | 기존 암호 기능의 값, 문자열 |
| G | contribution | 채팅 기여도 |
| H | user_id | 개인 식별 키, 양의 64비트 정수의 문자열 |
| I | leave_count | 일반 퇴장 횟수 |
| J | kick_count | 강퇴 횟수 |
| K | experience | 누적 경험치, 정수 문자열 |
| L | level | 경험치에서 계산한 레벨 |

`user_id`는 C# 내부에서 `long`, 시트에서는 **일반 텍스트**로 취급한다. 저장할 때 문자열과 `RAW` 옵션을 사용해 긴 ID의 반올림을 방지한다. 숫자 셀로 저장된 ID, 비어 있거나 잘못된 ID, 중복 ID, 잘못된 헤더는 불러오기를 중단한다. ID 없는 기존 행을 닉네임으로 연결하는 대체 경로는 없다.

사용자 DB 읽기가 실패하면 봇 시작과 저장이 차단된다. 실행 중 저장 오류는 봇을 중지시키고 채팅 DB 탭에 원인을 표시한다. 시트가 비어 보인다는 이유로 기존 내용을 지우는 동작은 하지 않는다.

### 퇴장·강퇴 집계

시트의 I·J열을 추가하고 기존 ID 계정의 두 횟수를 0으로 초기화했다. 기존 A:H 데이터와 보관용 `DB` 탭은 유지했다. 새 컬럼이 비어 있는 기존 행도 읽을 때 0으로 처리한다.

- `type=0` 시스템 메시지의 `feedType=2`는 일반 퇴장으로 `LeaveCount`를 1 올린다.
- `feedType=6`은 강퇴로 `KickCount`만 1 올린다. 강퇴를 일반 퇴장 횟수에 중복 합산하지 않는다.
- 대상은 `member.userId` 또는 `members[].userId`로 식별한다. 시스템 로그의 작성자나 내보낸 관리자의 ID를 대상 계정으로 사용하지 않는다.
- 미등록 대상은 자동 등록하며, 닉네임이 없어도 확인된 ID로 집계한다.
- 일반 사용자가 같은 문구를 입력하거나 `/퇴장`을 직접 입력해도 횟수는 올라가지 않는다.
- 수신 커서가 처리한 로그를 제외하며, 같은 이벤트의 중복 대상과 최근 동일 방·로그·사용자 조합도 차단한다.
- `/조회` 결과에 퇴장 횟수와 강퇴 횟수가 표시된다. 기존 `/퇴장` 안내 응답은 유지한다.

**새 버전으로 수신을 시작한 뒤의 이벤트부터 집계**한다. 과거 채팅 전체를 다시 읽어 횟수에 더하지 않는다. 퇴장·강퇴 횟수는 수신 묶음 처리 직후, 안내 응답 전에 저장한다. 저장 실패 시 대기 상태를 유지하고 중지·재시작에서 재시도하며, 미저장 상태에서는 창 닫기를 완료하지 않는다. 그 밖의 사용자 변경은 기존 약 60초 주기로 저장한다. DB_UserId를 공유하는 방을 바꾸어 사용하면 같은 사용자 ID의 횟수에 합산된다.

선택된 방의 기존 복호화 사본에서 퇴장 이벤트의 `feedType=2`와 `member(userId,nickName)` 구조를 확인했다. 해당 사본에는 강퇴 사례가 없어 강퇴 구분은 [node-kakao 원본 타입 정의](https://github.com/storycraft/node-kakao/blob/stable/src/chat/feed/feed-type.ts) 및 [대상 멤버 구조](https://github.com/storycraft/node-kakao/blob/stable/src/chat/feed/chat-feed.ts)를 확인하고 모의 이벤트로 검증했다. 실제 사용자를 내보내는 시험은 하지 않았다.

## 명령어 사용법

| 명령 | 대상 판정 |
| --- | --- |
| `/출첵` | 메시지 작성자 ID. 같은 날짜의 중복 보상 차단 |
| `/조회` | 메시지 작성자 ID |
| `/조회 @사용자` | 실제 카카오톡 멘션의 ID |
| `/좋아 @사용자 [숫자]` | 작성자 ID의 포인트를 차감하고 멘션 ID의 인기도 상승 |
| `/싫어 @사용자 [숫자]` | 작성자 ID의 포인트를 차감하고 멘션 ID의 인기도 하락 |
| 퀴즈 답변 | 답변을 보낸 작성자 ID에 보상 |
| 채팅 기여도·랭킹 | ID별 집계, 화면에는 닉네임 표시 |
| `/암호검증`, `/암호변경` | 요청자 ID와 일치하는 1:1 메시지만 처리 |

다른 사람을 지정할 때는 `@` 입력 후 **카카오톡 멘션 후보에서 한 명을 선택**해야 한다. 이름만 적거나 `@이름`을 일반 문자열로 붙여 넣으면 대상 ID가 없어 거부한다. 대상이 DB에 없으면 해당 ID로 자동 등록한 뒤 조회·인기도 처리를 계속하므로, 대상이 먼저 메시지를 보낼 필요는 없다. 초기 이름은 방 프로필에서 확인하고, 프로필이 없으면 멘션 표시 이름을 사용한다. 기존 계정의 이름·자산은 이 과정에서 덮어쓰지 않는다.

인기도 명령의 숫자는 양의 정수이며 생략하면 10이다. 같은 ID에 대한 자기 거래, 잔액 부족, 숫자 범위 초과는 차감 전에 거부한다. 동일한 닉네임이어도 ID가 다르면 별도 사용자로 처리한다.

암호 요청은 5분 후 만료된다. 1:1 방의 상대 ID와 메시지 작성자 ID가 모두 요청 ID와 일치해야 한다. 오픈프로필 등으로 그룹과 1:1의 ID가 다르거나 같은 ID의 방을 하나로 확정할 수 없으면 처리하지 않는다. 닉네임으로 우회 연결하지 않는다. 실제 암호 내용은 봇 채팅 로그에 추가하지 않는다.

토론 주제의 `Winner`와 응답 문구의 닉네임은 표시용 기록이다. 이 값으로 계정을 찾거나 자산·인증을 처리하지 않는다.

## 코드에서 사용하기

```csharp
User user = Database.Instance.AddUser(authorId, nickname);
User target = Database.Instance.GetOrAddUser(mentionedUserId, mentionNickname);
Database.Instance.FindUser(authorId, out user);
bool alreadyAttended = Database.Instance.CheckAttendance(authorId, nickname);

long targetId;
int amount;
if (command.TryReadTarget("/좋아", true, out targetId, out amount))
{
    string error;
    Database.Instance.ChangePopularity(command.AuthorId, targetId, amount, true, out error);
}
```

- `User.UserId`는 생성자에서 설정하고 외부에서 바꿀 수 없다.
- `UserTable`은 읽기 전용 목록이다. 등록은 `AddUser(long, string)`을 사용한다.
- `GetOrAddUser(long, string)`는 미등록 사용자를 만들고 기존 사용자는 그대로 반환한다. `AddUser`는 작성자의 새 닉네임도 갱신한다.
- `Bot.Chat`, `Bot.QuizAnswer`, 명령 대기열은 `AuthorId`를 전달한다.
- 암호 대기 상태는 `Dictionary<long, ...>`이며, 1:1 수신 감시는 `WatchDirect(long authorId)`로 시작한다.

## 적용과 검증

1. 기존 실행 중인 봇을 종료한다.
2. 이 저장소의 솔루션 전체를 다시 빌드하고 기존 설정·인증 파일을 사용하는 봇을 실행한다.
3. 채팅방을 선택하고 DB 수신을 시작한다. 새 메시지의 작성자부터 ID 계정이 생성된다.
4. 퇴장·강퇴 횟수 변경은 수신 처리 직후 `DB_UserId`에 저장한다. 그 밖의 변경에는 약 60초 저장 주기가 적용된다.

- 프로젝트 빌드 성공. 기존 미사용 변수 등의 경고는 남아 있다.

## 퇴장 저장 누락 수정 (2026-09-21)

토론아레나 서브방에서 10:27:52 발생한 일반 퇴장과 1초 뒤 봇 안내 메시지를 확인했다. 해당 대상은 시트에 없었지만, 이벤트 해석과 미등록 사용자 추가 경로는 정상 동작했다. 기존 구현에는 60초 저장 주기 전 종료 시 변경사항을 저장하지 않는 경로가 있었다.

퇴장·강퇴 변경을 같은 수신 묶음에서 즉시 저장하고, 저장 성공 후에만 저장 대기 상태를 해제하도록 수정했다. 저장 실패 시 재시도와 창 닫기 보류를 추가했다. 실제 DB에서 확인된 누락 퇴장 1건은 해당 ID의 새 계정을 만들어 퇴장 1·강퇴 0으로 복구했다. 그 외 과거 기록은 재집계하지 않았다.

검증: 미등록 사용자 및 두 횟수의 함께 저장, 중복 이벤트 추가 저장 방지, 저장 실패 시 대기 유지, 재시도 후 중복 증가 없음. 사용자 ID 테스트 18개와 명령 연결 테스트, 프로젝트 빌드를 통과했다.
