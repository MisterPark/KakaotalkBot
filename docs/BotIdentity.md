# 고정 봇 ID와 새 스프레드시트

## 연결

- 새 DB: https://docs.google.com/spreadsheets/d/12EdLFoc0uLGsRr5TX36CEqj2tO8PVrDzYICfEUHAmeI/edit
- 기존 DB의 셀과 공유 설정은 이관 과정에서 변경하거나 삭제하지 않습니다.
- 새 DB에는 기존 18개 탭과 키 확인용 `DB_Identity` 탭이 있습니다.
- 사용자 식별 컬럼은 `bot_user_id`입니다. JSON 이력 안의 `UserId`, `AuthorId`, `RevokedBy` 값과 사용자 ID가 포함된 복합 키도 `bot_...` 값으로 저장합니다.
- 메모 작성자, 칭호 부여·취소자, 퀘스트 보상 키도 변환합니다. 방 ID, 메시지 ID, 시간, 포인트는 사용자 ID로 변환하지 않습니다.

## PC 이동

1. 기존 PC의 봇을 종료하고 최신 저장소를 다른 PC에 옮깁니다.
2. `KakaotalkBot/BotIdentity.json`을 반드시 함께 가져옵니다. 사용자 요청에 따라 비공개 Git에서 보관할 수 있게 프로젝트에 포함했습니다.
3. 빌드하면 EXE 옆에 이 파일이 복사됩니다. 실행 파일만 옮길 때도 `BotIdentity.json`과 기존 Google 서비스 계정 `credentials.json`을 함께 옮깁니다.
4. 기존 시트 ID가 남은 `settings.json`은 실행 시 새 시트 ID로 전환됩니다. 다른 설정은 유지합니다.

동일 키는 PC, 닉네임, 채팅방에 관계없이 동일 사용자를 동일 봇 ID로 변환합니다. 신규 사용자도 자동으로 처리하므로 별도 매핑 목록을 합칠 필요가 없습니다. 두 PC에서 동시에 봇을 운영하면 기존 시트 저장 방식에 따른 덮어쓰기 충돌이 생길 수 있으므로 한 PC만 운영합니다.

## 키 보관

`BotIdentity.json`의 `Key`는 실제 카카오톡 ID를 복원할 수 있는 비밀키입니다. 운영진에게 공유할 대상은 새 스프레드시트이며, 이 키나 키가 포함된 저장소·실행 폴더는 공유하지 않습니다. 키를 삭제하거나 새로 생성하지 마세요. 잃어버리면 비공개 Git 또는 백업에서 같은 파일을 복원합니다.

PC에 종속된 암호화는 사용하지 않습니다. 별도의 256비트 암호화 키와 256비트 인증 키로 AES-CBC와 HMAC-SHA256을 사용하며, ID 동일성 유지를 위해 전용 인증 키에서 IV를 결정적으로 유도합니다. 인증 태그를 확인한 뒤에만 복호화합니다. 이는 사용자 ID 전용 형식이며 일반 메시지 암호화 용도로 사용하지 않습니다.

## 런타임과 저장 경계

카카오톡 DB, 명령 처리, 멘션 전송은 원래 `long user_id`를 사용합니다. `GoogleSheetHelper`가 시트를 읽을 때 복원하고 저장할 때 변환합니다. 시트에는 실제 ID와 변환 키를 기록하지 않습니다. 식별자 컬럼에 실제 ID가 들어 있거나 키가 다르면 읽기·저장을 실패시켜 기존 데이터를 보호합니다.

일반 텍스트의 알려진 사용자 ID도 봇 ID로 바꿉니다. 개인정보 전체를 익명화하는 기능은 아니므로 닉네임과 메모의 내용은 그대로 보입니다. `DB_Identity`에는 비밀키가 아닌 키 일치 확인값만 기록합니다.

## 검증과 이관 도구

- `tests/Test-BotIdentity.ps1`: 동일성, 64비트 정밀도, 다른 키·변조 거부, 방·로그 ID 보존, 각 이력의 왕복 변환을 검사합니다.
- `tools/IdentityMigration.cs`: 원본 읽기, 로컬 변환, 새 시트의 데이터·서식 복원에 사용한 도구입니다. 기존 원본 ID로의 복원 쓰기를 차단합니다.
- `tools/VerifyIdentityMigration.cs`: 새 시트를 읽어 전체 값·수식을 대조하고 봇의 실제 저장/읽기 경로를 검사합니다. `--write-check`는 기존 사용자 값을 변경 없이 새 DB에 다시 저장합니다.
- 이관용 원본 스냅샷은 Git에서 제외된 `artifacts/IdentityMigration` 아래에 보관합니다. 실제 ID가 포함된 파일이므로 운영진에게 공유하지 않습니다.

원본을 삭제하는 작업은 사용자가 직접 수행합니다. 기존 DB에 대한 접근 권한과 과거 다운로드 자료는 새 ID 도입만으로 없어지지 않습니다.

## 슈퍼관리자와 관리 권한

`BotIdentity.json`의 `SuperUserId`에는 슈퍼계정의 `bot_...` ID를 저장합니다. 닉네임으로 권한을 판정하지 않습니다. 설정을 바꾸면 봇을 재시작해야 하며, 다른 PC에도 같은 설정 파일을 복사합니다.

슈퍼관리자는 실제 명령 작성자 ID로 확인한 코드몽키 계정 하나입니다. 방장·부방장 여부, 닉네임 변경, 대법관 선거 활성화 여부와 관계없이 봇의 관리 명령을 사용할 수 있습니다. 같은 닉네임을 사용하는 다른 계정에는 권한을 부여하지 않습니다.

`/내보낸목록`, `/내보내기`, `/내보내기해제`는 선거를 켜지 않아도 동작합니다. 슈퍼관리자는 명부 수신이나 봇 작성자 ID 수동 입력이 완료되지 않았어도 목록 조회와 해제를 요청할 수 있습니다. 내보내기는 별도로 최신 명부에서 대상과 보호 계정, 중복 닉네임을 검사합니다. 중지된 봇, 변경된 방·수신 세션, 오래된 명령은 실행하지 않습니다.

봇 내부 슈퍼관리자 권한은 카카오톡 계정의 방 관리 권한을 바꾸지 않습니다. 카카오톡에서 관리 메뉴를 제공하지 않으면 매크로 중단 사유를 응답합니다. 일반 방장·부방장·대법관의 관리 요청은 최신 참여자 정보와 봇 계정의 실제 방장·부방장 권한을 확인합니다.

`tests/Test-ModerationAccess.ps1`은 합성 계정으로 슈퍼관리자 예외, 사칭 거부, 명부·세션 검사와 실제 명령 접수 경로를 검증합니다. UI 입력과 실제 채팅 전송은 실행하지 않습니다.

관리 메뉴는 Windows 메뉴의 항목 이름·좌표 직접 조회 → 고정 아이콘·저장된 메뉴 이미지 탐색 → OCR 순서로 찾습니다. `오픈채팅 관리`는 사용자가 제공한 `ModerationAssets/openchat-management-icon.png`를 대상 방의 `EVA_Menu` 왼쪽 아이콘 열에서 찾아 최초 실행부터 OCR 없이 선택합니다. 아이콘이 여러 곳에 있으면 선택하지 않습니다. 그 외 직접 그리는 메뉴는 최초 OCR로 확인한 영역을 실행 폴더의 `ModerationAssets/MenuCache`에 저장해 다음 요청부터 이미지로 찾습니다. 같은 프레임에 OCR을 반복하지 않으며, 배율·테마가 달라 이미지가 맞지 않으면 다시 인식합니다. 작은 팝업도 탐색하지만 다른 방의 메뉴, 채팅 본문, 중복 문구는 선택하지 않습니다. 인식 실패 시 실행 폴더의 `moderation-menu.log`에 메뉴 후보 정보를 남깁니다.

`tests/Test-ModerationMenu.ps1`은 작은 메뉴와 소유 관계, Windows 메뉴 문자열 조회, 이미지 저장·재사용·위치 변경·중복 거부를 검사합니다. 메뉴를 표시하거나 실제 앱에 입력하지 않습니다.

오픈채팅 관리 창이 열리면 해당 방에 연결된 내용 영역과 스크롤바를 확인한 뒤, `ModerationAssets/banned-member-management-button.png` 버튼을 이미지로 찾습니다. 보이지 않으면 내용 영역에서 아래로 스크롤하고 다시 찾습니다. 이미 열린 관리 창도 이어서 사용합니다. 화면이 더 움직이지 않거나 최대 20회에 도달하면 종료하며, 이 단계에서는 OCR이나 설정 변경 버튼을 사용하지 않습니다. 테스트에는 여러 화면을 내려가야 나타나는 버튼, 잘린 버튼, 이미 보이는 버튼, 맨 아래 정지와 실행 중 취소를 포함합니다.

내보낸 목록 객체의 방 식별 필드는 `chatId`이며 `linkId`와 다릅니다. 목록 조회·해제는 선택 방의 `ChatId`로 모든 행을 검증합니다. 실제 목록 창만 읽으며, 일반 채팅 목록 컨트롤은 제외합니다. 구조·소유 관계·방 ID가 맞지 않으면 읽기 실패로 처리합니다. `tests/Test-BannedMemberMemory.ps1`에서 ID 혼동, 이름·날짜 읽기, 빈 트리, 다른 방·손상된 트리·중복 ID 거부를 검사합니다.

목록 창이 생성된 직후에는 항목 트리가 비어 있고 서버 응답 뒤에 행이 들어옵니다. 목록 조회와 해제 모두 최대 10초 동안 읽기를 재시도하고, 같은 창의 사용자·이름·내보낸 시각이 500ms 동안 유지된 목록을 사용합니다. 이미 열려 있던 창도 동일하게 검사합니다. 현재 메모리 구조에서는 0명 상태와 로딩 중 상태를 구별할 수 없으므로, 0명이 계속되면 `로딩 완료를 확인하지 못했습니다`로 중단하며 기존 저장 목록을 비우지 않습니다. 실제 빈 목록을 성공으로 확정하려면 별도의 로딩 완료 신호 확인이 필요합니다. `tests/Test-BannedListLoading.ps1`은 0명→6명 전환, 느린 응답, 부분 로딩, 창·행 변경, 취소와 시간 초과 시 결과 저장 방지를 검사합니다.

`/내보내기`는 OCR이나 닉네임 검색 입력을 사용하지 않습니다. 참여자 목록은 `CGroupInfoWnd` → `CChatMemberListCtrl` → `CHAT_MEMBER_ITEM_DATA` 연결에서 명령의 사용자 ID와 방 ID를 검증하고, 해당 사용자의 실제 프로필 버튼 위젯 좌표를 읽습니다. ID 0인 항목은 대상에서 제외합니다. 내부 캐시에는 해제 후 채팅 메시지나 다른 화면 객체로 재사용된 주소도 남을 수 있으므로, 객체 종류·항목 역참조·목록 역참조·방 ID가 모두 맞는 참여자만 수집합니다. 검증된 행 수가 현재 활성 행 수와 정확히 일치해야 결과를 사용하며, 실제 행을 하나라도 읽지 못하거나 불필요한 후보가 더 발견되면 중단합니다. 회귀 테스트에는 활성 참여자 84개와 재사용된 캐시 21개가 섞인 실제 실패 조건을 포함합니다.

프로필 위젯의 좌표는 스크롤 내용 기준이므로 `CCustomScrollCtrl`에서 읽은 이동량을 빼고 목록 창의 원점을 더해 클릭 위치를 계산합니다. 대상 근처에서는 한 칸씩 스크롤해 지나치지 않도록 하며, 완전히 표시된 버튼만 클릭합니다. 클릭 직전 ID·닉네임·좌표를 다시 읽으며, 최신 명부의 보호 대상·역할·동명이인 검사도 유지합니다. 목록 열기·프로필 메뉴·내보내기·최종 확인 버튼은 이미지로 찾습니다. `tests/Test-ModerationParticipantSearch.ps1`은 OCR 구성 요소 없이 ID·이름·스크롤 좌표를 검증하고, ID 0·캐시 항목이 섞인 목록, 대상 근처에서 반복 스크롤하던 현상, 잘못된 방·소유 관계·중복 ID·손상된 목록·화면 밖 좌표를 검사합니다.

## 퀴즈 등록 권한

`/퀴즈등록 분류 | 난이도 | 문제 | 정답 | 힌트 | 해설`은 해당 방의 방장 또는 슈퍼계정만 가능합니다. 부방장은 등록할 수 없습니다. `/상식퀴즈`, `/퀴즈`, 분류별 퀴즈 호출, `/퀴즈목록` 조회와 정답 참여는 누구나 가능합니다. 등록·삭제는 메모리에 즉시 반영하며 기존 주기에 따라 상식퀴즈 시트와 동기화합니다. 자세한 동작은 QuizSynchronization.md를 참고하세요. 방장 권한은 수신 세션에서 확인한 최신 참여자 정보로 검사하며, 오래되거나 확인 중인 정보는 허용하지 않습니다.

문제 삭제는 등록과 동일한 권한으로 `/퀴즈삭제 분류 | 문제 전체 문장`을 사용합니다. 정확히 일치하는 한 행만 삭제하며, 중복된 행이 있으면 삭제하지 않습니다. 진행 중인 문제를 삭제하면 해당 퀴즈를 종료하고, 다른 문제의 진행 상태는 유지합니다. 시트를 직접 정렬하거나 편집하는 동안에는 삭제 명령을 동시에 실행하지 마세요. 삭제 직전 원문 재확인은 하지만 Google Sheets는 행 삭제에 조건부 원자적 비교 기능을 제공하지 않습니다.
