# 사용자 ID로 멘션 전송 조사

## 확인한 내용

- 현재 `WindowsMacro.SetTextToChatroom()`은 `@닉네임`을 붙여넣고 처음 발견한 후보 컨트롤을 클릭한다. 선택 대상의 사용자 ID를 검증하지 않는다.
- 실제 PC의 `보룸봇 테스트방`에서 전송 없이 `@`를 입력해 후보창을 열었다.
- 접근성 정보에는 입력창 `RichEdit Control`과 후보 컨테이너만 나타났다. `1006`, `1148`은 컨트롤 번호이며 카카오톡 사용자 ID가 아니다.
- 이번 접근성 관찰만으로는 후보별 `user_id`를 얻지 못했다. 화면 캡처는 `SetIsBorderRequired ... 0x80004002` 오류로 사용할 수 없었다.
- 진단용 `@` 입력과 검색어를 지웠다. 메시지는 보내지 않았다. 테스트방은 Escape 처리 중 닫혔다.

이 결과는 사용자 ID로 멘션할 방법이 없다는 증거가 아니다. 입력창 내부 객체와 전용 클립보드 형식은 추가 확인이 필요하다.

## 실제 멘션 복사 결과 (2026-09-21)

사용자가 멘션 후보에서 선택해 복사했다고 확인한 `@보룸봇`을 검사했다.
클립보드 소유 프로세스가 `KakaoTalk`인 것을 확인한 뒤, 게시된 형식의 원본 바이트를 읽었다.

| 형식 | 크기 | 내용 |
| --- | --- | --- |
| `CF_UNICODETEXT` | 10바이트 | `@보룸봇`과 문자열 종료 문자 |
| `CF_LOCALE` | 4바이트 | 텍스트 언어 정보 |
| `CF_TEXT` | 8바이트 | `@보룸봇`과 문자열 종료 문자 |
| `CF_OEMTEXT` | 8바이트 | `@보룸봇`과 문자열 종료 문자 |

RTF, HTML, 카카오톡 전용 등록 형식은 없었다. 일반 텍스트 비교 단계와 숫자 ID 패턴 검사는 수행하지 않았다.
관찰된 모든 문자열 데이터가 표시 이름으로만 구성되어 있어, 이 샘플에서는 복사 과정에 대상 ID가 유지되지 않았다.

따라서 현재 확인한 `Clipboard.SetText`/붙여넣기 경로에 사용자 ID를 추가하는 방식으로는 정확한 멘션을 구현할 수 없다.
카카오톡 입력창 내부 멘션 객체를 ID로 생성·선택하는 방법 또는 전송 데이터에 ID를 넣는 다른 경로를 추가 조사해야 한다.
이 시점에는 입력창 내부 객체를 조사하지 않았다. 이후 진행한 COM·메모리 검증은 아래 절에 기록했다.

실제 원본 보고서는 `artifacts\MentionClipboardProbe\Diagnostics\20260921-055953-fa46c3d1\report.txt`에 저장했다.
해당 폴더는 Git 추적에서 제외되며, 진단 도구는 클립보드 내용이나 카카오톡 DB를 수정하지 않았다.

## 클립보드 비교 도구

저장소에서 다음을 실행한다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Start-MentionClipboardProbe.ps1
```

생성 위치는 `artifacts\MentionClipboardProbe\MentionClipboardProbe.exe`다.
보고서와 형식별 원본 바이트는 해당 exe의 `Diagnostics` 하위 폴더에 자동 저장된다.

1. 카카오톡 테스트방 입력창에 멘션 후보를 선택하지 않은 일반 `@이름`을 준비한다.
2. 입력창의 해당 문자열을 선택해 Ctrl+C로 복사하고 진단 창의 **1. 일반 텍스트 수집**을 누른다.
3. 같은 이름을 멘션 후보에서 실제로 선택한다. 선택된 멘션만 Ctrl+C로 복사하고 **2. 선택된 멘션 수집**을 누른다. 전송은 하지 않는다.
4. 대상 `user_id`를 이미 알면 비교란에 입력하고 **ID 비교 다시 실행**을 누른다.

두 단계는 어느 순서로 수집해도 된다. 도구는 카카오톡이 복사한 클립보드만 읽고, 붙여넣기·키 입력·메시지 전송을 하지 않는다.
일반 텍스트, RTF, HTML, 등록된 전용 형식을 구분하고 원본 바이트를 저장한다. 이미지와 파일 목록은 수집하지 않는다.
한 형식당 4MiB, 전체 16MiB까지만 읽으며 클립보드 객체를 역직렬화하지 않는다.

ID 검사는 십진 문자열, UTF-16 문자열, 64비트 정수의 바이트 패턴을 찾는다. 일치는 후보일 뿐 멘션 구조나 대상 지정 성공을 증명하지 않는다.
같은 표시 문자열을 가진 일반 입력과 실제 멘션에서만 달라지는 형식이 있는지 먼저 비교해야 한다.

## 결과에 따른 다음 단계

- 전용 형식이나 RTF에 사용자 ID가 있으면 필드 구조를 분석하고, 카카오톡이 해당 형식의 붙여넣기를 멘션으로 받아들이는지 검사한다.
- 문자열만 복사된다면 클립보드만으로 멘션 객체를 구성할 수 있다고 결론내리지 않는다. 입력창 내부 멘션 객체 또는 다른 전송 경로 조사가 필요하다.
- 송신 기능을 연결하려면 대상 채팅방과 사용자 ID를 지정할 수 있어야 하며, 실제 송신 후 `attachement.mentions[].user_id`로 결과를 별도 확인해야 한다.

현재 봇의 전송 함수는 이 조사로 변경하지 않았다. 정확한 멘션 전송이 된다고 가정하는 구현을 추가하지 않는다.

참고: [GetClipboardData](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclipboarddata), [표준 클립보드 형식](https://learn.microsoft.com/en-us/windows/win32/dataxchg/standard-clipboard-formats).

## 입력창 COM·메모리 검증 (2026-09-21)

### 실행 환경과 확인 결과

카카오톡 `26.8.1.5315`의 `보룸봇 테스트방`에서 사용자가 준비한 `@보룸봇` 멘션을 조사했다.
이 결과는 해당 버전·실행 세션에서 검증한 것으로, 다른 버전의 메모리 오프셋을 보장하지 않는다.

1. 입력창은 컨트롤 ID `1006`의 RichEdit이다. 방 제목과 소유 프로세스가 일치하고 입력창이 하나일 때만 조사한다.
2. `WM_GETTEXT`에서는 공백만 읽혔다. `AccessibleObjectFromWindow(OBJID_NATIVEOM, IID_ITextDocument)`는 성공했다.
3. TOM으로 읽은 내용은 `U+FFFC` + 공백 + CR이었다. `GetEmbeddedObject()`로 카카오톡 내부 객체를 가져왔다.
4. 객체의 `IOleObject.GetUserClassID()` 결과는 `459e8c62-070f-42b0-b92b-64dd59af0ebe`였다.
5. 객체는 `IOleObject`, `IDataObject`를 제공했다. 검사한 `IPersist`, `IPersistStorage`, `IPersistStream`, `IDispatch`는 제공하지 않았다.
6. `IDataObject`는 텍스트 형식 1·13을 열거했으나, 이번 외부 COM 호출의 `GetData` 결과 매체는 `TYMED_NULL`이었다. 여기에서 ID를 얻지는 못했다.
7. 해당 방의 DB에서 확인한 보룸봇 ID `8172472438151128507`을 읽기 전용 메모리 검색으로 대조했다.
8. 같은 CLSID를 반환하는 가상 함수 테이블을 가진 객체 안에서 해당 ID를 찾았다. 이 샘플의 ID 위치는 객체 시작점 `+0xC0`였다. 닉네임도 인접해 있었다.
9. 입력창의 내부 포인터에서 해당 객체까지 연결되는 경로를 찾았다. 단순히 프로세스 전체에서 ID가 발견됐다는 것보다 범위를 좁힌 결과다.

객체의 CLSID는 가상 함수 테이블의 `IOleObject.GetUserClassID` 슬롯과, 실제 함수가 읽는 GUID 상수를 대조했다.
대상 프로세스의 함수를 원격 실행하거나 DLL을 주입하지 않았다.

### 삭제·복원 대조

테스트용 입력 내용을 선택해 Backspace로 지우고, Ctrl+Z로 복원했다. 메시지를 전송하지 않았다.
UI 접근성 값은 키 입력 직후 갱신이 늦어, 별도 COM 조회 결과와 다음 접근성 조회로 실제 반영 여부를 확인했다.

| 상태 | TOM 내부 객체 | 알려진 ID의 전체 검색 후보 | 입력창에서 해당 객체로 연결 |
| --- | --- | --- | --- |
| 원래 멘션 | 1개 | 12개 | 발견 |
| 입력 삭제 | 없음, 내용은 CR | 12개 | 조사 범위에서 발견되지 않음 |
| 실행 취소로 복원 | 1개, 같은 CLSID | 12개 | 다시 발견 |

삭제해도 ID 바이트는 메모리에 남았다. 따라서 **ID 검색 결과 자체를 현재 입력 중인 멘션으로 취급하면 안 된다.**
원래 멘션은 복원된 상태다. 쓰기·전송 API는 아직 연결하지 않았다.

실제 보고서:

- 원래 상태: `artifacts/MentionInputProbe/Diagnostics/20260921-072424-5c7c1ca8/report.txt`
- 삭제 상태: `artifacts/MentionInputProbe/Diagnostics/20260921-072556-d932acdb/report.txt`
- 복원 상태: `artifacts/MentionInputProbe/Diagnostics/20260921-072606-0173325a/report.txt`
- 여러 객체를 열거하도록 정리한 코드의 재확인: `artifacts/MentionInputProbe/Diagnostics/20260921-072722-e4726b8f/report.txt`

보고서의 주소는 이 실행 세션에서만 유효하다. 포인터 검색은 영역 단위의 제한된 탐색이므로, 기록된 모든 경로가 현재 활성 객체의 정식 필드라는 의미는 아니다.
복원 시 포인터 탐색 4,096개 영역 제한에 도달한 경우도 보고서에 표시했다.

- 프로그램은 키 입력·클립보드 변경·프로세스 메모리 쓰기·메시지 전송을 수행하지 않는다. 삭제·복원 대조는 별도로 수행한 UI 실험이다.
- COM 조회는 최대 4,096문자·32개 객체만 검사한다. 프로그램 종료까지 COM 호출이 대기하는 상황은 실행한 진단 프로세스를 종료하여 중단할 수 있다.

### 구현으로 이어질 조건

현재 확인한 것은 **입력 멘션이 별도 객체이고, 해당 객체 안에 대상 사용자 ID가 있다는 점**이다.
다른 사용자 멘션으로 같은 필드가 그 사용자의 DB ID로 바뀌는지를 추가 대조해야 한다.
그 다음 버전·객체·입력 위치·채팅방을 검증하는 조회 API를 분리하고, 멘션 생성/대상 변경을 구현한다.

`+0xC0`에 값을 쓰는 것만으로 송신 대상이 바뀐다고 결론내리지 않는다. 표시 이름·참가자 캐시·추가 내부 필드의 관계도 확인해야 한다.
송신 단계의 최종 성공 기준은 수신 DB의 `attachement.mentions[].user_id`가 요청한 ID와 일치하는 것이다.

참고: [AccessibleObjectFromWindow](https://learn.microsoft.com/en-us/windows/win32/api/oleacc/nf-oleacc-accessibleobjectfromwindow), [ITextRange.GetEmbeddedObject](https://learn.microsoft.com/en-us/windows/win32/api/tom/nf-tom-itextrange-getembeddedobject), [IOleObject.GetUserClassID](https://learn.microsoft.com/en-us/windows/win32/api/oleidl/nf-oleidl-ioleobject-getuserclassid).

### 현재 입력 객체 식별

폭넓은 포인터 탐색 경로를 그대로 송신 코드에 사용하지 않았다. 현재 버전에서 다음 관계를 따로 확인했다.

- 멘션 객체의 `IOleObject.GetClientSite` 구현이 읽는 포인터는 객체 `+0x80`이다.
- 사이트 객체 `+0x30`은 해당 입력창의 RichEdit 편집 객체를 가리킨다.
- 사이트 객체 `+0x38`은 원래 멘션 객체로 되돌아가는 포인터다.
- 사이트 객체 `+0x40`의 위치 값과 TOM에서 얻은 객체 위치를 대조한다. 이번 실제 샘플은 위치 0이다.
- 표시 문자열은 멘션 객체 `+0x38`의 문자열 자료구조에서 읽었다. 이번 샘플은 `@채팅봇`이다.

이 관계와 버전·CLSID·입력 객체 개수가 모두 맞는 경우만 조회를 성공으로 처리하는 `KakaoInputMentions`를 추가했다.
다른 방의 객체, 과거 객체, 일대일 대응을 확인하지 못한 후보는 사용하지 않는다.
여러 멘션·긴 표시 이름·다른 문자 위치의 실제 시험은 아직 수행하지 않았다. 실패하거나 모호한 경우에는 추정하여 쓰지 않는다.

### 추가한 API

소스: `KakaotalkBot/KakaoInputMentions.cs`. 프로젝트의 Compile 항목에도 포함했다.

```csharp
// 64비트 STA 스레드에서 호출한다.
InputMentionSnapshot snapshot = KakaoInputMentions.Read("보룸봇 테스트방");
foreach (InputMention mention in snapshot.Mentions)
{
    long userId = mention.UserId;
    string displayText = mention.DisplayText;
    int position = mention.Position; // TOM 문자 위치이며 수신 DB의 at 값과 다르다.
}
```

## 자동 준비·봇 연결 구현 (2026-09-21)

`/입장` 응답은 `Command.AuthorId`를 대상으로 멘션과 본문을 한 메시지로 보낸다.
`WindowsMacro.SetTextToChatroom()`의 닉네임 선택 후 즉시 전송하던 경로를 제거하고,
`SendMentionToChatroom()`으로 교체했다. 이 단계에서는 Google Sheets의 닉네임 사용자 DB를 유지했으며,
이후 [사용자 ID 기준 DB 전환](사용자ID전환.md)에서 개인 식별과 사용자 저장소를 ID 기준으로 변경했다.

### 처리 순서

1. 현재 채팅창과 계정 프로세스, 지원 버전, 입력창이 비어 있는지 확인한다.
2. 입력창을 활성화하고 `@후보닉네임`을 유니코드 키 입력으로 넣는다. 클립보드는 사용하지 않는다.
3. 해당 채팅창이 소유한 `EVA_Window_Dblclk` 팝업 안의 후보 컨트롤(ID 1148)을 더블클릭한다.
4. TOM과 메모리 조회로 위치 0에 개인 멘션 객체 하나가 생성됐는지 확인한다. `@all`은 거부한다.
5. TOM으로 본문을 붙이고, 기존 API로 멘션 ID만 요청한 64비트 `user_id`로 바꾼다.
6. 입력 전체, 객체 주소·소유자·ID, 대상 창, 입력 포커스를 재확인한 후 Enter를 한 번 게시한다.
7. 입력창이 비워지는지 확인한다. 이 완료 판정은 서버 수신 확인이나 상대방 알림 확인을 의미하지 않는다.

닉네임은 개인 멘션 객체를 만들기 위한 검색어다. 최종 대상은 ID로 지정하므로 동명이인이 선택돼도
그 후보의 ID를 그대로 사용하지 않는다. 닉네임 검색 결과가 없으면 전송을 중단한다.
표시 이름을 메모리에 별도로 덮어쓰지 않으며, 본문에 멘션 하나를 앞에 붙이는 형태를 지원한다.

### 호출 API

```csharp
// 기존 봇에서 사용하는 단일 호출. 현재 STA 스레드에서 실행한다.
WindowsMacro.Instance.SendMentionToChatroom(
    TargetWindow, command.AuthorId, command.Nickname, parsedAnswer, SelectedRoom.ProcessId);

// 외부에서 단계별로 사용할 때. Prepare는 메시지를 보내지 않는다.
var sender = new KakaoMentionSender("보룸봇 테스트방");
var ready = sender.Prepare(8172472438151128507L, "채팅봇", "본문\n둘째 줄");
// 실제 전송을 원하는 경우에만 호출한다.
sender.SendPrepared(ready);
// 전송 대신 준비를 취소하려면 SendPrepared 대신 DiscardPrepared(ready)를 호출한다.
```

`SendPrepared()`는 같은 인스턴스가 반환한 미전송 결과만 받는다. 전송을 시도한 결과는 다시 사용할 수 없다.
전송 도중 오류가 나거나 결과가 불명확해도 재전송하지 않는다.
준비 도중 실패하면 마지막으로 확인한 자체 입력과 일치하는 내용만 정리하며, 사용자가 수정한 내용은 보존한다.
입력창 안내 문구는 정확한 문구와 글자색(#949494), 실행 취소 이력을 확인한다. 빈 입력임을 확정하지 못하면 중단한다.
봇의 멘션 실패는 봇 수신을 중지하고 GUI 채팅 탭 상태란에 원인을 표시한다.
일반 본문을 이어 보내는 대체 동작은 하지 않는다. 원인과 채팅방을 확인한 후 수동으로 다시 시작한다.

### 안내 문구 오인 수정

빈 입력창의 `메시지 입력\r`에서도 `EM_GETMODIFY`가 참(-1)을 반환해 준비가 차단되는 현상을 재현했다.
같은 상태에서 실행 취소 가능 여부는 0이고, 안내 문구의 TOM 글자색은 `0x949494`였다.
수정 여부 플래그를 판정에서 제거하고, 정확한 안내 문구·문구 전체의 글자색·실행 취소 이력을 함께 확인한다.
접근성 값은 실제 입력에서도 비어 있을 수 있어 판정 근거에서 제외했다.
문서 재조회 때 안내 문구 판정도 비교하여 조회 도중 서식이나 입력 상태가 바뀌면 중단한다.

수정 전 `IsEmpty=False`였던 동일 입력이 수정 후 `IsEmpty=True`로 반환됐으며,
해당 안내 문구 상태에서 개인 멘션 자동 준비 → ID 변경 → 본문 결합 → 정리를 약 3초에 통과했다.
추가 메시지는 전송하지 않았다. `tools/MentionPlaceholderProbe.cs`는 문구·수정 플래그·실행 취소 가능 여부·서식을 읽기만 하는 진단 도구다.
